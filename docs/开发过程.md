# MiRemote 的开发过程

MiRemote 起源于一个实际需求：Mac mini M4 本身没有内置麦克风，希望能按住一个实体按键说话，通过微信输入法完成语音输入，减少键盘打字。起初尝试使用游戏耳机、蓝牙耳机和独立按键设备，但游戏与语音输入之间切换不够方便；看过带按键的无线麦克风，也考虑过现成遥控器方案。

最早使用 Google TV 遥控器配合已有的 vRemoter 项目探索语音输入，过程中遇到连接、音频时长和响应体验等问题。后来决定尝试手边已有的小米蓝牙语音遥控器，并将小米方案做成独立应用。开始时并不知道这只遥控器的麦克风能否在 Mac 上工作，因此先分别验证按键和音频，再决定如何接入。

## 先解决按键识别

通过专门的按键诊断工具，逐个按下实体按键并记录 macOS 收到的 HID 事件，建立电源、语音、方向、确认、主页、返回、菜单和音量键的对应关系。测试对象为一只小米蓝牙语音遥控器，设备标识为 VID `0x2717`、PID `0x32b8`；这不代表其他小米遥控器都兼容。

第一版映射能触发设置的快捷键，但遥控器原始按键同时也会生效。尝试使用 HID 独占方式未获系统允许后，改用 `hidutil` 针对匹配的设备及其位置设置按键规则，屏蔽已识别的原始按键，再发送用户选择的映射事件。规则避免覆盖其他程序已有的映射，正常关闭映射或退出时恢复。实机测试中，遥控器的原始操作被拦截，普通键盘仍可使用。

随后补充按住和释放事件：音量键长按持续调节，方向键长按持续移动，松开后停止；单独的修饰键也能保持按下和释放。关闭窗口等一次性操作不重复触发。上述音量和方向键行为经过遥控器实机测试。

## 确认麦克风真的可以用

仅看到语音服务和音频数据包，不能证明人声可用。项目先通过蓝牙低功耗（BLE）连接遥控器语音服务，协商后主动发送开启麦克风指令；测试中按住语音键可收到音频数据。接着使用已有 ATVV 协议和 ADPCM 解码实现生成一小段本地 WAV，试听确认人声清晰。这一步把“有数据”和“声音能用”分开验证。

确认后，独立的小米遥控器应用接入语音服务：启用遥控器麦克风后，在语音键按住期间接收和解码音频，再送入虚拟音频设备。语音键继续使用用户配置的按键映射，不额外重复发送快捷键。测试时，将微信输入法的麦克风选为虚拟设备，使用遥控器说话后成功识别出文字。

## 独立虚拟音频驱动

早期测试复用了已有的 `vRemoteDr 2ch` 虚拟音频设备。为了让小米方案拥有自己的音频设备，项目基于 BlackHole v0.5.0 源码构建独立的 `MiRemote` 驱动，使用独立设备标识，并保留相应 GPL 源码与许可证。应用优先检测 MiRemote，也识别旧的兼容设备；检测输入输出流只能证明设备被系统枚举，不能单独证明完整音频链路可用。

安装需要管理员权限。一次尝试通过 `launchctl` 重新启动音频服务被系统完整性保护拒绝，因此安装步骤改为提示保存工作并重启 Mac。重启后系统识别出 MiRemote，遥控器应用显示 HID 和 BLE 连接，微信输入法选择 MiRemote 后实测可以识别语音。

## 把调试结果做成可用界面

应用增加了可配置的按键映射、菜单栏常驻、遥控器电量和权限状态。权限窗口分别检查输入监控、辅助功能、发送按键事件，以及 HID、BLE 和音频设备状态；语音关闭时，BLE 状态显示为未检测。

收音区区分“服务就绪”和“正在收到音频”，用分段音量格与实际数字电平（dBFS）展示解码后的输入信号。dBFS 是数字信号电平，并非经过校准的环境声压值。停止收音或一段时间未收到数据时，音量显示归零。

按键界面则根据遥控器外形制作三维模型，固定正面视角，用引线将 12 个实体按键连接到各自的映射和识别控件；音量键外形也作了圆角调整。固定视角的目的是让引线始终对应实体按键的位置。

## 开源与验证边界

项目整理出应用源码、驱动对应源码及构建、安装和卸载脚本，并公开到 GitHub。应用和驱动均从源码重新构建过；应用安装到隔离目录后成功启动，检测到遥控器和音频设备，微信输入法语音识别也经过实机确认。构建脚本包含引线布局、音量计算与按键行为自检。

这些结果不等于所有设备都已验证：目前的实体测试集中在上述一只小米遥控器与开发时使用的 macOS 环境；其他遥控器、系统版本及完全干净的机器首次安装和授权流程仍需验证。当前应用使用本地 ad-hoc 签名，尚未经过 Apple 公证；安装驱动需要管理员权限并重启。安装及使用细节请以仓库 README 和脚本为准。
